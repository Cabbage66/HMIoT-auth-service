# 数据库设计说明

## 一、是否应一次性给出总数据库设计

本项目应先给出一版总的系统数据库基线设计，但不应把它视为最终不可变设计。

原因如下：

* 当前项目需求和测试方案已经确定，核心业务边界清晰，包括用户管理、USB 认证、终端绑定、动态生物绑定、物联网设备绑定、SSO、跨域互认、信任评估和审计日志。
* 这些核心链路存在强关联，如果不先设计总体数据模型，后续会在用户、设备、绑定、策略、票据、信任评估之间反复改表，影响开发效率。
* 正规项目中应采用“基线库表 + 版本化迁移”的方式管理数据库。第一版给出完整主干表，后续需求变化通过 `V2/V3/...` 增量 SQL 演进，不直接反复修改已执行过的 `V1`。

因此，本项目采用以下策略：

* `V1__baseline_schema.sql`：建立完整主干表结构，覆盖已确定需求。
* 后续新增字段、索引、约束、字典数据时，新建 `V2__xxx.sql`、`V3__xxx.sql`。
* 开发早期如果数据库尚未正式部署，可调整 `V1`；一旦进入联调或多人开发，应冻结 `V1`，只追加新迁移。

## 二、SQL 文件位置

后端基线 SQL 文件：

```text
backend/src/main/resources/db/migration/V1__baseline_schema.sql
```

该路径遵循 Flyway 默认迁移目录规范。当前即使暂未接入 Flyway，也可作为 MySQL 初始化脚本手动执行。

建议后续在 `backend/pom.xml` 中接入 Flyway：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

接入 Flyway 后，Spring Boot 启动时会自动执行 `db/migration` 下未执行过的迁移脚本。

## 三、数据库选型

规划数据库：MySQL 8.x。

字符集与排序规则：

```sql
utf8mb4
utf8mb4_0900_ai_ci
```

原因：

* 支持中文、英文、符号等完整字符集。
* MySQL 8 原生支持 JSON 字段，便于保存外部系统响应、模型输入输出、策略配置、终端事件原文等半结构化数据。
* 与 Spring Boot、MyBatis/MyBatis-Plus、Flyway 集成成熟。

## 四、表设计分组

### 1. 管理员与用户

| 表名 | 作用 |
|---|---|
| `sys_admin` | 管理员账号、角色、登录状态 |
| `user_account` | 用户基础信息 |
| `user_profile` | 用户扩展属性、后量子系统属性 |
| `registration_request` | 用户注册申请与审核记录 |

支撑能力：

* 管理员登录。
* 用户注册、审核、驳回。
* 用户信息查看与更新。
* 后量子属性获取后写入用户扩展属性。

### 2. 统一实体、设备与绑定

| 表名 | 作用 |
|---|---|
| `entity_identity` | 用户、设备、物体等统一实体身份 |
| `device_entity` | 业务终端、物联网设备、摄像头、感知节点 |
| `terminal_info` | 登录终端、安卓终端、网页终端信息 |
| `iot_device_status` | 物联网设备接入与状态 |
| `binding_relation` | 用户与终端、动态生物、物联网设备、应用资源的绑定 |

支撑能力：

* 管理员添加业务终端、设备、物体。

* 用户绑定动态生物特征。
* 用户绑定广域低功耗物联网设备。
* 登录和访问时进行绑定关系校验。

### 3. 证书与生物特征

| `biometric_auth_record` | 生物认证流水、分数、阈值、失败原因 |

支撑能力：

* 证书签发、绑定、吊销、审计。
* USB 认证模块挑战签名认证。
* 声纹注册、声纹比对。

### 4. 应用资源与策略

| `security_baseline` | 终端安全基线策略 |
| `policy_publish_record` | 策略下发与执行记录 |

支撑能力：

* 配置应用安全等级。

* 支持用户登录、功能访问、二次认证等策略场景。
* 向客户端下发策略并记录执行结果。

### 5. 认证、票据与单点登录

| 表名 | 作用 |
|---|---|

## 六、关键设计原则

### 1. 统一实体与具体业务表分离

`entity_identity` 保存用户、设备、物体等统一实体身份。人员用户仍以 `user_account` 为主，设备和物体以 `device_entity` 为主。

这样设计的目的：

* 满足“身份信息不只限于人员，还覆盖用户、设备、物体”的需求。
* 避免把设备/物体强行塞进用户表。
* 支持后续人、机、物之间的统一关联映射。

### 2. 绑定关系使用通用关系表

`binding_relation` 采用 `subject_type + subject_id + target_type + target_id + relation_type` 结构。

这样可以支持：

* 用户绑定终端。
* 用户绑定动态生物特征。
* 用户绑定物联网设备。
* 用户绑定应用资源。
* 后续扩展设备绑定设备、终端绑定物体等关系。

### 3. 策略内容使用 JSON 保存

`auth_policy.auth_chain`、`security_baseline.rule_config` 使用 JSON。

原因：

* 认证协议编配存在组合方式、调用顺序、比对模式、场景条件等变化项。
* 开发初期不应过早拆成过多策略子表，否则实现成本高。
* 后续若策略复杂度稳定，再将 JSON 中的核心字段拆分成子表。

### 4. 模型输入输出保留原文

信任评估请求和结果均保留 JSON 原文。

原因：

* `UEBA4.2` 模型输入输出可能随模型调整变化。
* 保留原文便于调试、复现和审计。
* 业务决策字段仍单独结构化保存，例如信任等级、分数、是否异常、决策结果。

### 5. 审计日志独立

`audit_log` 独立保存关键操作，不依赖业务表的更新时间。

必须记录：

* 管理员登录。
* 用户新增、修改、审核。
* 证书签发、吊销。
* 生物审核、撤销。
* 绑定、解绑。
* 认证成功、认证失败。
* 票据签发和验证。
* 跨域互认。
* 策略发布。

## 七、后续演进建议

### 1. 第一阶段不要过度拆表

当前 `V1` 已覆盖主链路。早期实现时建议优先完成核心字段读写，不要为了极端通用性提前拆出大量中间表。

### 2. 联调后再补精细索引

当前 SQL 已为常用查询添加基础索引。等接口和页面确定后，再根据真实查询增加复合索引。

### 3. 大日志表后续考虑分表

以下表后续数据量可能较大：

* `terminal_event`
* `audit_log`
* `biometric_auth_record`
* `ticket_verify_record`
* `trust_assessment_request`
* `trust_assessment_result`

演示阶段先单表即可。正式环境可按月分表或冷热归档。

### 4. Flyway 迁移命名建议

```text
V1__baseline_schema.sql
V2__add_seed_admin.sql
V3__add_policy_detail_table.sql
V4__add_terminal_event_indexes.sql
```

规则：

* 已执行的迁移文件不再修改。
* 新变更只追加新版本文件。
* 每个迁移文件只做一个清晰主题。

## 八、当前未写死的内容

以下内容不应在数据库第一版中过度固定：

* 真实 USB Key 厂商 SDK 字段。
* 真实后量子系统返回属性全集。
* 动态生物系统详细模型字段。
* 广域低功耗系统真实设备协议字段。
* 异构跨域系统真实票据协议字段。
* UEBA 模型内部特征字段。

这些内容目前通过 JSON 字段和外部调用记录保留扩展空间，等真实接口稳定后再结构化。
